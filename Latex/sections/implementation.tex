The purpose of this chapter is to showcase how the design was realized in the final build of the prototype used for the participant study. As previously stated, instead of restaging Figure~\ref{fig:referenceSingleCycleDatapath} as a three-dimensional machine, the system appears as a spatial route through a sequence of local teaching spaces coordinated by a runtime structure that keeps the active instruction, lesson mode, progression state, validation rules, and resulting architectural state in agreement from beginning to end.

The prototype is examined here through the structures that make that lesson possible: the shared lesson framework that keeps the route coherent, the environment through which the session unfolds, the objects and interfaces that represent architectural state, the six phases through which instruction execution is carried, and the three-mode variation that formed the final study baseline.

\section{Platform and Development Context}

The prototype was developed in Unity v. 6000.4.11f1 and deployed as a Virtual Reality application. The build relies on Unity's XR Interaction Toolkit v.~3.4.1 and the Unity VR Template as part of the baseline interaction and project setup foundations, alongside OpenXR support v.~1.16.1 and Meta OpenXR support v.~2.5.0 for the VR systems required by the staged lesson \cite{unityXrInteractionToolkitManual,unityVrTemplateManual}.

The broader visual environment was assembled with the help of free Unity Asset Store packs, most notably the Free LowPoly SciFi Pack by Cuboom \cite{cuboom2018lowpoly} and 3D Sprite Sci-Fi Props by Oiva Kahri \cite{kahri2023scifi}. These assets reduced the need to construct every mesh from scratch, and assisted the creation of the various props, interactables, and overall environment scene. These technical foundations served as enabling conditions that helped realize the project to its completion. The project source repository for the final build is available at \url{https://github.com/Norged-Out/CompArchVR}.

\section{Overall System Architecture}

At the broadest level, the prototype is organised around one shared lesson structure that keeps the active instruction, lesson mode, phase progression, validation state, and resulting architectural changes aligned across the whole route, implemented chiefly through \texttt{CpuLessonFlow}. This internal coherence allows the lesson to behave as one continuous walkthrough rather than as a set of disconnected stations. A learner-facing guide layer, anchored by \texttt{LessonGuideController}, ties that shared state to the visible panels, prompts, and support surfaces distributed across the route.

The route always knows which instruction is active, which mode is governing support, which phase owns the next action, which decisions have already been validated, and what resulting state must be handed onward. The phase-local lesson systems therefore do not run continuously in parallel in the manner of hardware, but activate when the shared lesson flow places the learner in that part of the route and return control once the required work is complete, thus enabling the learner to follow through one coherent account of execution as presented in Figure~\ref{fig:datapathToVrTranslation}.

This shared structure also supports all three lesson modes by reusing the same broad routes and central objects, while changing how much help is shown, how much must be reconstructed, and how strict later validation becomes. These mode-specific differences are governed centrally so that panel visibility, hint availability, and validation tolerance remain consistent throughout the route. In that respect, the implementation directly realizes the progression already outlined in Chapter 4 and summarised in Figure~\ref{fig:modeProgression}: support is reduced across the modes, while the underlying lesson remains recognisably the same.

The prototype thus represents a bounded instructional system driven by authored lesson definitions that store the identity, operand structure, and expected lesson behaviour of each supported instruction, rather than a full processor simulator. Guided lesson definitions, stricter encoded-instruction variants, and local reference content all feed the same broader walkthrough rather than branching into unrelated sub-systems.

\section{Environment Structure and Lesson Routing}

The entire lesson is staged inside one authored scene that functions as part of the teaching structure. As Chapter 4 argued, and as Figure~\ref{fig:referenceSingleCycleDatapath} makes clear, the standard single-cycle datapath is compact, simultaneous, and densely connected. The final environment redistributes the major stages of instruction execution into a progressive route that preserves the broad order of the datapath while giving each local decision a clearer setting in which to be understood.

\subsection{Scene Organisation}

As Figure~\ref{fig:routedLessonMap} shows, each major phase occupies its own authored zone within the route. The lesson begins in an introduction and fetch area that establishes the mode, provides the initial interface context, and stages the opening handoff of the instruction. Decode sits beside the register bank because that is the point at which encoded fields begin turning into specific operand choices and immediate handling. Execute follows as a distinct station, allowing ALU-related reasoning to be treated locally. Memory access sits beside the visible data memory structure, while write-back and program-counter update occupy the later parts of the route so that final architectural consequence and control flow can be experienced as the closing stages of the lesson.

This organisation is intended to isolate tasks without breaking the broader execution story. Register selection benefits from being staged beside persistent architectural objects. Execute benefits from clearer separation between the values entering the phase, the control-facing choices that govern it, and the result it produces. Memory access benefits from enough local space for address, stored word, and resulting transfer to appear as related but still distinct ideas. Program-counter update benefits from standing apart as a concluding area in which branch or jump consequence can be treated as the final conceptual step of the route. The result is a route that presents one part of the execution story at a time without severing it from the machine as a whole.

Because these panels are tied to the current lesson state, they expose only the support, prompts, and interaction context relevant to the active instruction, phase, and mode.

\section{Representation of Architectural State}

One of the central implementation problems concerned the appearance of architectural state once the datapath had been translated into VR. In the standard diagram, some of the most important relationships are carried by buses, register-file reads, memory access, multiplexers, and control decisions that remain visually compact or fully implicit. The final build had to represent enough of that structure to support reasoning while remaining usable as a guided lesson rather than collapsing into manual busywork. The solution was a family of visible objects and interactions that externalise selected relationships without attempting to surface every internal detail literally.

\subsection{Instruction Representation}

The opening representation of the active instruction appears during fetch as a physical instruction module transferred between two terminals. In textbook single-cycle terms, this stands in for the point at which the current instruction becomes available from instruction memory under program-counter control, stored in the instruction register. Within the lesson, that availability is staged as a concrete handoff that marks the learner's entry into the route.

\subsection{Register Representation}

The register file is represented as a physical 32-register bank placed beside the decode region, accompanied by a larger state display that presents the same contents in a more readable overview. Each register remains a persistent architectural object with a stable identity and stored value. This directly supports one of the main learning outcomes established in Chapter 4: recognising which registers a supported instruction reads from or writes to and connecting those identities to later state change.

\begin{figure}[htbp]
\centering

In the standard datapath, register access is compact and mostly internal, and the significance of \texttt{rs}, \texttt{rt}, or \texttt{rd} is usually inferred from field labels and a small register-file box. Here, the bank gives those relationships a stronger presence, as the source and destination registers can be approached, selected, validated, and revisited. That visibility matters later as well, because write-back is easier to understand as an actual update to the architectural state already in play than as a merely local station event.

\subsection{Datapackets and Value Flow}

Once the lesson moves beyond register selection, the focus shifts to which value is now moving and what later phase depends on it. The implementation answers that problem through datapackets. A datapacket is a portable learner-facing object that carries a value already produced or retrieved, whether that value comes from a register, an immediate, the ALU, memory, or a later control-flow calculation.

Figure~\ref{fig:datapackets} shows this translation clearly. Instead of asking the learner to imagine internal buses carrying \texttt{Read Data 1}, \texttt{Read Data 2}, an immediate, an ALU result, or a memory value, the build gives those states a portable physical identity. This helps abstract the hardware by preserving the reasoning structure that later stages depend on: a value was sourced or produced here, and that exact value must now be carried onward correctly.

This is also where sign extension becomes pedagogically visible. In an ordinary datapath explanation, the immediate may be shown entering an extender and then simply treated as ready for later use. In the implemented lesson, the immediate is externalised through its own transformed datapacket so that the learner can see that a raw immediate is not merely copied forward unchanged. The route therefore makes sign extension legible as part of operand preparation rather than leaving it as a silent internal conversion.

\subsection{Scanner Representation}

Owing to its namesake, scanners were introduced to make value recognition and local validation into learner actions. A scanner accepts either a register token or a datapacket, checks that it matches the expected role for the current instruction, and then either produces the next required state or unlocks the next relevant transition. This is one of the clearest ways in which the implementation redistributes otherwise hidden datapath relationships into visible lesson work.

\subsection{Control Signals}

Control is represented less as one hidden learner-facing control unit than as a distributed set of explicit choices that appear in the later phases of the route. In the textbook datapath shown in Figure~\ref{fig:referenceSingleCycleDatapath}, decode largely determines how execute, memory, write-back, and next-PC behaviour should proceed, often through centralised signal generation and multiplexer selection. The prototype does not automate this process, instead choosing to surface selected control-facing decisions where doing so helps the learner understand why later stages behave as they do.

If every control consequence remained internal, the later phases would risk becoming passive confirmations of a decision already made elsewhere. By distributing certain control-facing choices across execute, memory access, write-back, and program-counter update, the implementation gives those later phases clearer instructional weight while still keeping the overall route within a bounded scope.

\subsection{Memory Representation}

Data memory is represented as a visible wall of authored memory words, coupled to a local address-and-value display and to transfer behaviour at the memory-access station. This gives memory a persistent place in the centre of scene rather than reducing it to a hidden lookup or a panel-only display. The memory wall stands in for address-dependent access to stored data while giving the learner a visible distinction between address, stored word, and transferred result.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.85\linewidth]{DataMemoryWall.jpg}

\label{fig:dataMemoryWallImpl}
\end{figure}

Load and store instructions often cause difficulty because they require the learner to connect register values, offsets, addresses, stored contents, and later updates into one chain of reasoning. By making memory visible in place, as in Figure~\ref{fig:dataMemoryWallImpl}, the implementation gives that chain a stronger local structure than a compact internal datapath branch usually provides on a first pass.

\section{Implementation of the Lesson Phases}

The route is experienced as six implemented lesson phases that realise, in slower and more local form, the broad logic already outlined in Figure~\ref{fig:datapathToVrTranslation}. Each phase gives one part of instruction execution its own objects, interactions, and validation rules. What is followed here is the reasoning of instruction execution as it was staged for a guided supplementary lesson rather than the literal timing of the hardware itself.

\subsection{Instruction Fetch}

Fetch begins in the introduction area, where the active lesson mode and current instruction context are already known. The learner activates the fetch terminal, receives the instruction module, and carries it to the decode terminal to begin the rest of the route. This is a clear pedagogical staging of a process that the textbook datapath handles internally and with much greater simultaneity.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.82\linewidth]{InstructionModuleDocking.jpg}
\caption[Instruction-module docking during fetch]{The instruction module being docked at the decode terminal after its transfer from the fetch area. This handoff marks the learner's transition from acquiring the active instruction to interpreting its encoded fields and preparing operands.}
\label{fig:instructionModuleDocking}
\end{figure}

The implemented fetch phase gives the route a definite beginning. The learner undergoes an explicit transition from instruction availability to instruction interpretation, and the remainder of the lesson is anchored to that opening handoff. Unlike the textbook style, the process is abstracted and simplified to produce a softer opening to the lesson process, with the module acting as a physical but not literal representation of an Instruction Register.

\subsection{Decode and Operand Preparation}

Decode is the densest part of the implementation because it is where the instruction stops being an inert object and becomes the usable lesson context for everything that follows. In Learning mode, the phase introduces the instruction structure step by step, surfaces the relevant fields, and prepares the learner for source-register selection and any immediate-related work.

Practice and Test change the point of entry into this phase, with the learner seeing an encoded instruction that must be reconstructed with less or no support before later stages become available. This is where mode variation is strongest, because decode is the place at which the instruction first becomes actionable lesson state rather than merely a selected item.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.84\linewidth]{InstructionDecodePracticeMode.jpg}
\caption[Reduced-support decode in Practice mode]{Decode in Practice mode, where the instruction is presented in encoded form and the learner must reconstruct the relevant field structure with less support than in Learning mode. The figure illustrates how the same decode task is retained while explanatory scaffolding is reduced.}
\label{fig:instructionDecodePracticeMode}
\end{figure}

Operand preparation then carries that state forward, as the learner retrieves the required source registers from the bank, places them on the correct scanners, and receives the resulting datapackets used downstream. Where an immediate is needed, the lesson also prepares that value in a form suitable for later use through the extender-linked transformation already shown in Figure~\ref{fig:datapackets}, allowing sign-extension-related behaviour to become visible rather than remaining a quiet internal transformation. 

\subsection{Execute}

Execute is realised as a dedicated ALU station in which operand interpretation, operation selection, and result production become local tasks. The learner must supply the appropriate values, set the relevant control-facing options (\texttt{ALUSrc} and \texttt{ALUOp}), and complete the validation required for the active instruction before the result datapacket (\texttt{ALUResult} or \texttt{ZeroResult}) is produced. This gives ALU reasoning enough local presence without overloading the user with information pertaining to logic gates or surfacing mux-like decisions.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.84\linewidth]{AluValidationLearningMode.jpg}
\caption[ALU validation during execute]{Execute-phase validation in Learning mode, showing operand handling and the learner-facing ALU decisions required for the active instruction. The interaction makes operand choice, \texttt{ALUSrc}/\texttt{ALUOp}-related reasoning, and result production visible before the lesson continues.}
\label{fig:aluValidationLearningMode}
\end{figure}

In the standard datapath, ALU behaviour is often recognised in principle before it is understood in use. The implementation addresses that gap by slowing the process down and making later consequence depend visibly on earlier correctness, making it one of the clearest places where the lesson preserves the reasoning of the datapath while redistributing its internal compactness into a human-scale teaching phase.

\subsection{Memory Access}

Memory access handles the point at which the active instruction either interacts with data memory or passes onward without needing it. For load instructions, the learner must establish the correct address path before the memory wall reveals the targeted word and transfers the resulting data onward. For store instructions, the learner must supply both the correct address and the correct data before the update can occur. Instructions that do not use data memory are allowed to pass through without artificial interaction, which keeps the phase aligned with the actual architectural differences between instruction classes.

\begin{figure}[!htbp]
\centering
\includegraphics[width=0.84\linewidth]{MemoryAccessStationActivePracticeMode.jpg}
\caption[Memory-access interaction in Practice mode]{The memory-access station during reduced-support use. Address validation, memory-specific control choices, and the resulting load or store consequence are handled within one local interaction space so that the direction and effect of the memory operation remain visible.}
\label{fig:memoryAccessPracticeMode}
\end{figure}

The phase also surfaces the relevant control-signal decisions through \texttt{MemRead} and \texttt{MemWrite}, making the distinction between read and write behaviour part of the learner-facing interaction. Address calculation, stored value, loaded value, and later result use all appear here as connected but locally distinguishable ideas. Once a store updates memory, that change remains part of the lesson state in the data memory. Once a load retrieves a word, the resulting datapacket can be understood as coming from a visible memory location rather than from an abstract internal branch of the diagram.

\subsection{Write-Back}

Write-back became a full physical phase in the final build where the learner must identify whether register write-back should occur, determine the correct destination register, supply the appropriate result source, and validate the resulting update to the register bank. This gives the route a clear culminating moment at which earlier decisions resolve into a visible architectural consequence.

\begin{figure}[!htbp]
\centering
\includegraphics[width=0.84\linewidth]{WriteBackLearningModeControlSignals.jpg}
\caption[Write-back as a visible culmination]{Write-back interaction in Learning mode, where the learner identifies whether register write-back should occur, selects the destination and result source, and validates the register update. The phase makes the final architectural consequence of earlier datapath decisions visible at the register bank.}
\label{fig:writeBackLearningMode}
\end{figure}

Figure~\ref{fig:writeBackLearningMode} shows why this phase carries more weight than a compact textbook write-back event usually does on first encounter. It brings together the main interaction patterns established earlier in the route. The learner must confirm \texttt{RegWrite}, use \texttt{RegDst} to determine the correct destination register, and use \texttt{MemToReg} to determine the correct result source.

The implemented station gathers together work completed earlier in the route and makes the final update readable through both local interaction and the larger register-state display. Instructions that do not write to the register file simply bypass this stage, which preserves the selective structure already present in the standard datapath.

\subsection{Program Counter Update}

The final phase handles next-PC reasoning, branch consequence, and the limited jump behaviour supported in the study build. In a strict single-cycle account, these relationships are resolved in parallel within the same overall cycle, alongside other internal work. The implementation reorganises them into a dedicated concluding station so that control-flow consequence has a clear instructional place in the route.

\begin{figure}[!htbp]
\centering
\includegraphics[width=0.84\linewidth]{PcUpdateLearningModeBranchUi.jpg}
\caption[Program-counter update and branch consequence]{Program-counter update in Learning mode, where next-PC and branch-related consequences are treated as an explicit final lesson decision. Separating this reasoning from the earlier phases gives the learner a visible account of where execution proceeds next and why.}
\label{fig:pcUpdateLearningMode}
\end{figure}

Figure~\ref{fig:pcUpdateLearningMode} illustrates the logic of that decision. The aim is control-flow legibility over literal timing fidelity. \texttt{Branch} or \texttt{Jump} reasoning are difficult to absorb when they remain implicit or compressed into the same space as every other datapath consequence. By giving next-PC reasoning its own station, the lesson allows the route to close with a clear account of where execution would go next and why. 

This is the strongest example of pedagogical serialization in the build, as the next-PC reasoning is now separated out of the overall cycle to signify the control-flow consequence of the instruction while also leveraging the various gated-style logic that goes into address-target calculation to produce a visible teaching moment.

\section{Implementation of the Three Lesson Modes}

The three lesson modes share one route and one broad lesson architecture while changing the amount of support, tolerance, and independent reconstruction expected from the learner. In implementation terms, this realises the pedagogical progression already described in Chapter 4 and shown in Figure~\ref{fig:modeProgression}.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.84\linewidth]{LessonIntroUiModes.jpg}
\caption[Mode selection at lesson entry]{The lesson-introduction interface used to select Learning, Practice, or Test mode before instruction execution begins. The selected mode determines how much guidance, tolerance, and reference support is available while preserving the same overall lesson route.}
\label{fig:lessonIntroUiModes}
\end{figure}

\subsection{Learning Mode}

Learning mode is the most fully supported version of the lesson, which uses the guided instruction assets directly, keeps lesson panels fully visible, keeps phase information available, provides proper reference guides for resources and control signals, and presents the entire lesson in a more digestible and otherwise simplified but elaborate format.

Its entire responsibility is to provide the learner a full understanding of the VR experience and also ease them into the practical datapath system. It is fully guided and the learner receives the clearest progression support and feedback through the authored world-space interfaces. Its job is to establish the route and logic of the walkthrough rather than to stress-test independence.

The codebase also treats this mode as the baseline for the lesson, with all its assets, flow steps, and explanatory text providing the main sources from which the rest of the lesson architecture is derived.

\subsection{Practice Mode}

Practice mode reuses the same downstream route but changes the entry conditions and the strictness of later interactions. The instruction is shown in hexadecimal encoded form during fetch and in 32-bit binary form in decode, and the learner must complete a typed bitfield decode before the rest of the phase sequence becomes available.

As stated earlier, the greatest difference occurs during the Decode phase, making the breakdown more in line with the formal expectation of the actual datapath. The later phases are also refactored so that stricter behaviour could be introduced in the form of tighter attempt budgets, changing the reference guide into a limited hint availability that is dynamically provided based on what the learner has correctly answered, and held failure states across later phases. These are all implemented through the shared practice-policy systems and specific flows, rather than duplicating the phase controllers themselves.

\subsection{Test Mode}

Test mode is the harshest layer and is best understood as Practice with the supports stripped back even further. It reuses the assessment foundation already built for Practice mode, but removes most of the remaining supports. Instruction selection becomes randomized from the supported practice pool, hint surfaces are entirely disabled, lesson-facing support panels are entirely hidden, and validation tolerance is reduced to one mistake per relevant category in each phase, with each failure forcing a full lesson failure.

This mode did not require a new architectural path, as it is still the same datapath lesson route. The learner is simply asked to complete it under conditions that reveal whether the earlier supported understanding has become more independent, and make it a proper practical datapath experience.

\section{Implemented Content Baseline}

By the time the participant-study build was locked, the prototype supported a bounded but deliberate set of arithmetic, immediate, memory, branch, and one limited jump case. This baseline was wide enough to show that different instruction classes activate different parts of the datapath and therefore demand different forms of reasoning, while still remaining narrow enough for the lesson to stay stable, testable, and interpretable within the scope of the study.

\section{Technical Constraints and Deliberate Simplifications}

The final implementation reflects several boundaries that were both practical and intentional. The most obvious is scope. The prototype is centred on selected single-cycle MIPS instruction execution and does not attempt to cover the whole of assembly programming, multicycle behaviour, pipelining, hazards, or gate-level digital logic. That narrowing was necessary for the lesson to stay coherent enough to support the educational claim being made.

Another boundary concerns fidelity to actual hardware behaviour. The build remains grounded in the logic of the textbook single-cycle datapath, but does not preserve its hidden, parallel, and largely internal nature in literal form. Instructions are physically moved, decode is stretched into learner work, values are carried as datapackets, and some control-facing decisions are distributed across later stations. These simplifications were adopted because the project is framed as a pedagogical VR abstraction rather than as a hardware-faithful simulator.

There were also more ordinary implementation constraints. Scene-authored systems are easier to tune locally, but they require careful serialized wiring and make many controller relationships sensitive to scene organization. Decode in particular grew into the busiest area of the project because it sits at the meeting point of instruction identity, field interpretation, register preparation, immediate handling, and mode-specific difficulty. The prototype addressed that complexity by splitting support logic into helpers, while still keeping the whole lesson on one shared runtime.

\section{Summary}

The prototype was implemented as a scene-authored XR lesson system whose central concern is instructional coherence. One shared runtime coordinates instruction selection, lesson progression, local validation, and architectural state, while the environment itself presents the learner with a routed sequence of fetch, decode, execute, memory, write-back, and program-counter update stations.

The final build is therefore best read as a bounded teaching baseline. It includes the three-mode lesson structure, physical instruction handoff, register interaction, datapackets, immediate extension, ALU interaction, memory access, write-back, program-counter update, and the authored instruction, register, and memory baselines that support those systems. Together, these make up the implementation that was taken forward into the participant study.
